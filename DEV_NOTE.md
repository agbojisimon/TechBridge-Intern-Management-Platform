# Developer Note — TechBridge Task Management API (Task 7)

For Task 7, I built a backend API for the TechBridge internship platform and connected it to the Intern Dashboard I built in Task 6. The problem Task 6 left open was that every task was written directly inside a JavaScript array in the dashboard file, so the information was permanently trapped in the webpage. In Task 7 that array is gone. The dashboard now requests the tasks from a Node.js and Express.js server, and when a task status changes the change is sent back to the server instead of only being applied in the browser.

The project is split into a frontend folder and a backend folder. The backend holds server.js, which starts an Express server on port 3000, and a data folder where tasks.json stores the eight TechBridge internship tasks. That JSON file acts as a simple database, so the server reads it on every request and writes back to it whenever a task is created, updated or deleted. I kept a second copy, tasks.seed.json, so `npm run reset` can restore the original demo data after testing, which matters because the updates are saved to disk.

The API exposes GET /api/tasks to return all tasks, GET /api/tasks/:id to return one specific task, PUT /api/tasks/:id to update a task, and POST /api/tasks plus DELETE /api/tasks/:id for the optional challenges. I also added GET /api/health, which the dashboard calls to decide whether to show the backend as connected or offline. Every failure returns the same JSON error shape with a matching status code — 400 for a bad request, 404 for a task that does not exist — so the frontend always knows what to expect. The server validates the status against a list of allowed values instead of trusting whatever the browser sends, because a real API cannot assume the client is correct.

On the frontend side I put every fetch call in a separate file, js/api.js, and kept js/dashboard.js for rendering only. That separation makes the boundary between frontend and backend visible in the file structure, and it means the network code can be read in one place. The API helper converts any failure into a readable error message, so a stopped server and a mistyped URL are handled the same way in the dashboard.

The dashboard now shows a loading state with a spinner while it waits for the response, an error state that says "Unable to load tasks" with a Try Again button when the server cannot be reached, and an empty state when no task matches the current filter or search. Marking a task as completed sends a PUT request, disables the button while it waits, and only then updates the card, the completed count, the remaining count and the progress bar using the status the server returned. If the request fails, the task is left unchanged and a message explains why. The View Task button now requests a single task by id and shows it in the existing modal without refreshing the page, and the filters and the search box filter the tasks that came back from the API. I kept the filters working on the client side, as the task required, and also added the same filters as query parameters on the server.

One problem I had to solve was testing the offline state. When Express also serves the frontend, stopping the server means the page itself cannot load, so the error state would never be visible. I enabled CORS on the API so the dashboard can also be opened from a separate local server such as VS Code Live Server, and the offline behaviour can be demonstrated properly from that origin.

Another issue was that the tasks now come from an API and can be typed by a user through the add-task form, so building cards with string concatenation into innerHTML became a real injection risk. I added an escapeHtml helper and applied it to every value coming back from the API before it is placed in the page.

I kept the design consistent with the rest of the site by reusing the existing task cards, status pills, filter buttons, modal and colours, and only added new styles for the spinner, the error state, the connection pill, the toast messages and the add-task form. The whole project runs from one command, `npm start`, because Express serves the frontend folder as well as the API.
